Key idea: the laptop thinks (perception, task logic, the neural network); the Jetson owns the motor stream (it is the only writer of rt/arm_sdk); the Unitree board and the motor drivers do the real-time servo. The laptop never writes rt/arm_sdk itself (PickerIO refuses to start otherwise).

What the motor actually receives is not a voltage or a torque from us but a PD set-point per joint: (q*, dq*, kp, kd, τ_ff). The driver closes the loop locally at high rate. Example: RL mode kp = 100 N·m/rad, so an error of 0.1 rad pushes 10 N·m; kd = 10 adds damping. The policy was trained in Isaac with the same PD 100/10 and no feed-forward, which is why the real stack sends τ_ff = 0 in RL mode (gravity makes the arm sag ≈ g(q)/kp below the target, exactly as in sim). v20's own gains: arm MPC kp 390/kd 10 (set by the launch script), hold kp 400/kd 12, waist kp 380/kd 10.

Important: in the RL toys vision is open-loop. The apple is measured once with the arm at home, then the policy runs closed-loop only on the joints. Reasons: the arm blocks the view, and the camera points 48° down, so it never sees anything above its own height (only ~15% of the training targets are visible). Every calibration or depth error goes straight into the final palm error. --closer_cm and --calib correct a constant offset. The original picker does re-detect during the approach (redetect gate).

5. Communication: laptop ↔ robot

Two planes on the same cable. Control plane = ssh (sshpass, user unitree): clock sync, start/stop daemon and cameras, tail -F of the robot logs. Data plane = DDS (CycloneDDS, domain 0). Unitree topics (rt/...) and ROS 2 topics share the same DDS bus: ROS 2 maps /foo to the DDS topic rt/foo, which is why ROS tools can see Unitree messages. Laptop processes use fast_dds.py: the robot as a unicast peer with a 1 s announce, so discovery takes ~1 s instead of 20-35 s.

Serial: everything inside one control step (read → policy → send) and the phase sequence of the toy / SM. Concurrent but not parallel: the Python threads inside the daemon and inside the toy (one GIL; C code such as ACADOS, numpy, DDS can release it). Truly parallel: different processes (daemon parent vs publisher child, laptop processes, the Unitree firmware). Asynchronous coupling: nothing is clock-synchronised: 50 Hz policy, 2 ms poll, 90 Hz parent loop, 90 Hz child loop, 500 Hz lowstate all run on their own timers and hand data over as "latest value" (zero-order hold). This is simple and robust, but adds jitter (section 9).

9. Findings: likely problems and optimisation opportunities

Ranked by risk. "Verify" = I could not check the robot itself (the cable was down).

#FindingWhy it mattersSuggestion
1ORIGINAL mode has no robot-side watchdog or E-STOP. The deployed v20 ignores rt/arm_ctrl/heartbeat and estop (that was v22, never deployed). The SM's estop_link heartbeat goes nowhere; dashboard STOP in ORIGINAL is logged "ignored".If the laptop dies mid-move in the picker, MPC keeps driving to the last target. Only the Unitree remote's own damping / power is left.Add an ORIGINAL watchdog in the dual layer (hold the arm when the SM heartbeat goes silent while enabled), and honour STOP in ORIGINAL (call v20's own "stop").
2Lowstate stale > 0.2 s cuts the stream (v20 pub loop sets flag 0, the child stops). The firmware then grabs the arms at once — the same snap the shutdown hand-off fixed.Any GIL stall or cable glitch over 200 ms gives a sudden arm motion. dds_poll makes it rarer, not impossible.In the dual layer, on stale lowstate keep publishing a hold, or use the weight ramp (pub_weight) instead of a hard cut.
3Rate chain 50 → 90 → 90 Hz, unsynchronised. Each policy target is held 1 or 2 parent ticks (11 or 22 ms) and the child adds 0-11 ms. Docstrings say 250 Hz, but PUB_RATE_HZ defaults to 90 and nothing sets it (verify on the robot).Jitter and extra latency that Isaac never saw (sim applies each action for exactly 20 ms). A possible part of "same policy, different result".Use an integer multiple of 50 Hz (100 or 200 Hz) for both loops; fix the docstrings.
4One Python GIL for everything on the Jetson: 2 MPC threads, the 90 Hz loop, the 100 Hz RL tick, a 500 Hz poll loop, state thread, listeners.This was the root cause of the late lowstate / "stuck" stops (2026-10-16). The 2 ms poll is itself a constant GIL user.Poll with a DDS WaitSet (blocks in C) or 4-5 ms; pause the RL-side arm's MPC solver in RL mode; long term: C++ writer or policy onboard.
5The 50 Hz control loop crosses the cable twice (lowstate → laptop → policy → command → Jetson).Network + laptop scheduling in the loop; the lag gate and keep-alive are workarounds.The README's plan: run the policy (small MLP, numpy) in the daemon via RlMode.submit(); laptop sends only the apple and GO.
6Parent→child heartbeat uses wall time (time.time()), and sync_robot_clock.sh runs date -s on every launch, also when the daemon is reused.A backward clock step makes a hung parent look "fresh" to the child for as long as the step; a forward step drops a publish.Use time.monotonic() (system-wide clock, valid across processes); skip the clock sync when the daemon is reused.
7Contact torque guard is warn-only; collision protection relies on "stuck" (0.15 rad for 0.5 s).At kp 100 a blocked arm presses ~15 N·m for half a second before the stop.Calibrate the residual on the robot (logs exist), then enable --contact-torque-stop.
8Dex3 hand is commanded straight from the laptop (rt/dex3/right/cmd), with no robot-side watchdog.If the laptop dies while gripping, the hand does whatever its firmware does on silence (unknown).Check the Dex3 timeout behaviour; consider a hand hold/open in the daemon (v22 had it).
9Gravity feed-forward differs between modes: env.sh sets ARM_MPC_GRAVITY_FF=1.0 for MPC, the qref/RL path forces τ_ff = 0.Correct for RL (matches training) but makes ORIGINAL vs RL hold poses differ by the sag g/kp; confusing in comparisons.Keep, but document it; comment in env.sh says 0.15 while the value is 1.0.
10Doc/config drift: RELEASE_AFTER_S is unused (code goes FREEZE→RELEASE after 1 s, README says "STOP again or 5 s"); child "stale > 0.5 s" in its docstring vs 2.0 s in code; "250 Hz" in several places.Wrong mental model while debugging.Clean up the comments and the README table.
11Sticky RL + 120 s lost-laptop watchdog: the arm stays at kp 100 with no supervisor for up to 2 min.Not dangerous at rest, but nobody watches contact during that time (the guard only runs with an owner).Shorter timeout (e.g. 15-30 s), or keep the stuck guard on in idle hold.
12Open network: password "123" in scripts, host-key checks off, DDS without authentication.Anything on 192.168.123.0/24 can write rt/arm_rl/cmd or rt/arm_sdk.Fine on an isolated cable; never bridge it to Wi-Fi. SSH keys instead of sshpass.
13Deployment state unknown: dds_poll, pub_weight, the switch were built 2026-10-16; my notes say "not deployed yet".Debugging the wrong version.On the robot: md5 of ~/g1_arm_onboard/dual/*.py vs local; check the log lines "dds_poll: polled" and "[pub-proc] arm_sdk weight follows".
14Things that can be lost: ~/g1_fruits_picker (daemon layer, launcher, camera_extrinsics.yaml) is not a git repository, and tactile_calib.json sits in the git-ignored logs/.A disk failure loses the robot-side code and both calibrations.Put g1_fruits_picker under git (private remote); force-add the calibration files.
